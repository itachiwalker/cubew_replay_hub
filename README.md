# cubew_replay_hub

The replay-storage/relay backend for the "Share replay" feature in [cubew](https://github.com/itachiwalker/cubew) (a Rubik's Cube app). It runs on Supabase (PostgreSQL), and this repository manages only that schema definition (migrations). It's kept in a separate repository from the app's own code (`my_cube-base.html`) since the two have very different release lifecycles.

## How it works

- When a user shares a replay in the app, the client computes a SHA-256 hash (first 16 characters) of the replay data and saves it via the `upsert_replay` RPC
- The share URL takes the form `https://<app URL>/#s=<16-character hash>` (no sequential ID is ever included in the public URL — the hash itself is the lookup key)
- Opening the link fetches the data directly by hash via the `get_replay` RPC
- Data older than 30 days is automatically deleted daily via `pg_cron`
- The `anon` role is never granted direct table access — only execute permission on the RPC functions (since Supabase's REST API has no Origin-based access restriction, this is the only real line of defense)

See the development chat (Claude.ai) logs for the design background and the alternatives that were considered.

## Directory structure

```
supabase/
├── config.toml           # Generated by `supabase init` (for local dev; normally no need to edit)
└── migrations/
    └── *_initial_replay_schema.sql   # Table, RLS, RPC functions, and pg_cron job, all in one
```

## Deployment

This repository is connected to Supabase's GitHub integration (Project Settings → Integrations → GitHub). Any push/merge to the `main` branch automatically applies pending migrations under `supabase/migrations/` to the production project.

**Important**: once a project is on this migration-based workflow, don't edit the schema directly in the Supabase dashboard's SQL Editor — that desyncs the migration history and causes `db push` to fail. Any schema change must go in as a new migration file.

```bash
# To create a new migration locally
supabase migration new <a name describing the change>
# Write its contents, then commit and push — it deploys automatically
```

## RPC API (contract for the frontend)

### `upsert_replay(p_hash text, p_data jsonb) returns jsonb`

Saves a replay. The `status` field in the returned value tells you the outcome:

| status | meaning |
|---|---|
| `ok` | Saved successfully (either a new row, or an existing byte-identical one was reused). The `hash` field holds the 16-character hash |
| `collision` | A different payload already exists under the same hash (an astronomically unlikely collision). Nothing was saved |
| `invalid_hash` / `invalid_data` | The input didn't pass shape validation |

### `get_replay(p_hash text) returns jsonb`

Returns the replay data for `p_hash` (a 16-character hex string), or `null` if it doesn't exist.
